---
title: "Authentication"
description: "How to authenticate requests to your on-premise Context7 instance"
---

The on-premise API supports API keys for server-to-server and MCP access. Pass the key in the `Authorization` header:

```bash
Authorization: Bearer ctx7op-xxxxxxxx_xxxxxxxxxxxxxxxx
```

The server also accepts the key in the `x-api-key`, `context7-api-key`, or `context7_api_key` header.

Keys are scoped to the user account that created them and inherit that user's role (`admin` or `member`). There are no per-key scopes or expiry - revoke a key to invalidate it. A request with an invalid or revoked key gets `401`; it is not treated as an anonymous request.

## Creating an API Key

<Steps>
  <Step title="Open Settings">
    Go to **Personal Settings > API Keys** in the admin dashboard and click **Create API Key**.

    <Frame>
      ![API Keys settings page](/images/enterprise/api-keys/api-keys-empty.png)
    </Frame>
  </Step>
  <Step title="Name the key">
    Give the key a descriptive name so you know which client or service is using it (e.g. `CI pipeline`, `Cursor`).

    <Frame>
      ![Create API Key dialog](/images/enterprise/api-keys/api-keys-create-dialog.png)
    </Frame>
  </Step>
  <Step title="Copy the key">
    Copy the full key value before closing the dialog. It is only shown once.

    <Frame>
      ![API Key Created dialog showing the key value](/images/enterprise/api-keys/api-keys-created.png)
    </Frame>
  </Step>
</Steps>

<Warning>API keys are shown only once at creation. Store yours securely before closing the dialog.</Warning>

## Revoking a Key

Go to **Settings > API Keys** and click the delete icon next to the key. Revocation is immediate and cannot be undone. Update any integrations using the key before revoking.

## Roles

| Role | Access |
|---|---|
| `admin` | Full access to all endpoints including settings, user management, and delete operations |
| `member` | Can parse, refresh, search, and use MCP. Cannot delete libraries, cancel parses, import libraries, or access admin endpoints |

A personal API key acts with the role of its owner:

| Operation | Member key | Admin key |
|---|---|---|
| Parse and refresh libraries | Yes | Yes |
| Refresh Notion and Google Drive libraries | No | Yes |
| Delete libraries, cancel parses, download the support bundle | No | Yes |
| Import libraries (`/api/import-libraries`) | No | Yes |
| `/mcp` and `/api/v2` search and context | Yes | Yes |

Settings, user management, and other admin routes need an admin signed in to the dashboard. They do not accept API keys.

Default credentials on a fresh install are `admin` / `admin`. Change them immediately from **Settings > Change Credentials**.

## Anonymous Access

Certain operations can be opened to anonymous callers (no session and no API key). Configure them from **Settings > Permissions**:

| Permission | Default |
|---|---|
| Anonymous parse / refresh | Off |
| Anonymous delete | Off |
| Anonymous support bundle | Off |

These switches do not limit signed-in users: members and their API keys can always parse and refresh. The delete switch also covers cancelling a parse, and opens both actions and support bundle downloads to members.

<Note>
Earlier versions allowed anonymous parse and refresh by default.
</Note>

MCP authentication is configured separately in **Settings > Authentication**. When enabled, these endpoints require a dashboard session or a personal API key:

- `/mcp`
- `/api/v2/*`, including `/api/v2/libs/search` and `/api/v2/context`
- `GET /api/projects` and `GET /api/projects/{name}`
- `GET /api/projects/{name}/logs` and `GET /api/projects/{name}/search`
- `GET /api/queue`
- `GET /api/parse-status`

When disabled, those endpoints answer anonymous callers, and [library access rules](/enterprise/security/library-access) still filter restricted libraries. The bundled MCP server calls the v2 endpoints over loopback with a per-process token, so a reverse proxy on the same host does not bypass MCP authentication.
