Context7 On-Premise keeps your repositories, generated documentation, application database, vector store, and MCP server in your infrastructure. The content required for parsing, embedding, reranking, or source-code documentation is sent to the AI providers you choose. With an online license, the instance also contacts Context7 Cloud for license checks, a daily usage report, and public library results. See [Network and data flow](#network-and-data-flow).

## What's Included

- Full Context7 parsing and indexing pipeline
- Local vector storage (no external vector DB required)
- Built-in MCP server. Works with any MCP-compatible AI client
- Web UI for managing indexed libraries and configuration
- REST API compatible with the public Context7 API
- Private GitHub and GitLab repository ingestion

## Setup

<Steps>

<Step title="Request a trial">

Go to [context7.com/plans](https://context7.com/plans) and click **On-Premise Trial**. Fill out the request form. No credit card required. You'll receive a 30-day full-featured license key via email once approved.

</Step>

<Step title="Deploy">

Follow the deployment guide for your platform:

<CardGroup cols={2}>
  <Card title="Docker" icon="docker" href="/enterprise/deployment/docker">
    Deploy with Docker Compose
  </Card>
  <Card title="Kubernetes" icon="dharmachakra" href="/enterprise/deployment/kubernetes">
    Deploy on Kubernetes with raw manifests
  </Card>
</CardGroup>

</Step>

<Step title="Complete the setup wizard">

Open `http://localhost:3000` in your browser. On first launch, the setup wizard guides you through configuring:

1. **AI Provider** - Choose OpenAI, Anthropic, Gemini, AWS Bedrock, or a custom OpenAI-compatible endpoint. Enter the provider credentials and model name.
2. **Embedding Provider** - Use the same provider as your LLM, or configure a separate one for embeddings.
3. **Git Tokens** - Add a GitHub and/or GitLab token for the platforms you use.

All configuration is stored locally in the embedded database and can be updated later from the Settings page.

</Step>

<Step title="Ingest your first repository">

From the dashboard, click **Add Repository** and enter a GitHub or GitLab URL. Once ingestion completes, your private docs are ready to query.

You can also add libraries via the REST API with a personal API key (see [Authentication](/enterprise/api/authentication)):

```bash
curl -X POST http://localhost:3000/api/parse \
  -H "Authorization: Bearer ctx7op-..." \
  -H "Content-Type: application/json" \
  -d '{"repoUrl": "https://github.com/your-org/your-repo"}'
```

</Step>

</Steps>

## Connecting Your AI Client

The Context7 CLI is the recommended way to connect an AI coding agent. Install it once on the machine that runs your client:

<Tabs>
  <Tab title="Public npm registry">
    ```bash
    npm install --global ctx7@latest
    ```
  </Tab>
  <Tab title="Internal npm registry">
    ```bash
    npm install --global ctx7 \
      --registry https://npm.internal.yourcompany.com
    ```
  </Tab>
</Tabs>

For restricted or air-gapped environments, mirror the `ctx7` package and its dependencies in your approved internal npm registry. Once installed, on-premise setup does not contact npm, GitHub, or Context7 Cloud. It uses bundled rule and skill content and contacts only your deployment to discover its MCP authentication setting.

Pass the root URL of your deployment (without `/mcp` or `/api`) and select the client:

<Tabs>
  <Tab title="Claude Code">
    ```bash
    ctx7 setup --mcp \
      --base-url https://context7.internal.yourcompany.com \
      --claude
    ```
  </Tab>
  <Tab title="Cursor">
    ```bash
    ctx7 setup --mcp \
      --base-url https://context7.internal.yourcompany.com \
      --cursor
    ```
  </Tab>
  <Tab title="VS Code">
    ```bash
    ctx7 setup --mcp \
      --base-url https://context7.internal.yourcompany.com \
      --vscode
    ```
  </Tab>
  <Tab title="Codex">
    ```bash
    ctx7 setup --mcp \
      --base-url https://context7.internal.yourcompany.com \
      --codex
    ```
  </Tab>
  <Tab title="OpenCode">
    ```bash
    ctx7 setup --mcp \
      --base-url https://context7.internal.yourcompany.com \
      --opencode
    ```
  </Tab>
</Tabs>

Setup reads the deployment's MCP authentication setting. When MCP authentication is disabled, no credential is written. When it is enabled, the dashboard's Connect card presents two steps: sign in and click **Create API key**, then copy the command after the dashboard inserts the one-time-visible key. Select **Configure manually** to reveal the equivalent client-native configuration instead. If you run the base command without `--api-key`, the CLI requests the key with hidden input.

For non-interactive automation, provide the personal key through the environment:

```bash
CONTEXT7_API_KEY=ctx7op-... ctx7 setup --mcp --yes \
  --base-url https://context7.internal.yourcompany.com \
  --claude
```

You can use `--api-key ctx7op-...` instead, but command-line arguments may be retained in shell history. Setup writes the MCP client configuration, a Context7 rule, and a bundled `context7-mcp` skill. The bundled files mean the deployment does not need to expose Context7 Cloud's skill APIs.

<Note>
  Custom `--base-url` setup uses the deployment's Streamable HTTP endpoint. Hosted OAuth, local stdio transport, and CLI-query mode are not available for on-premise targets.
</Note>

### Manual configuration

If your client is not supported by `ctx7 setup`, point it at `<deployment-root>/mcp`. When MCP authentication is enabled, send the personal key as a standard bearer token:

```json
{
  "mcpServers": {
    "context7": {
      "url": "https://context7.internal.yourcompany.com/mcp",
      "headers": {
        "Authorization": "Bearer ctx7op-..."
      }
    }
  }
}
```

For other clients, see [All Clients](/resources/all-clients).

## Configuration

### Environment Variables

These are set in your `docker-compose.yml` or `.env` file before starting the container.

| Variable | Required | Description |
|---|---|---|
| `LICENSE_KEY` | Yes | License key issued by Upstash |
| `PORT` | No | HTTP port (default: `3000`) |
| `DATA_DIR` | No | Data directory inside the container (default: `/data`) |
| `DATABASE_URL` | No | Postgres connection string. Without it, the embedded SQLite database in `DATA_DIR` is used. See [Scaling](/enterprise/deployment/scaling) |
| `PG_POOL_MAX` | No | Postgres connection pool size per replica (default: `10`) |
| `ENCRYPTION_KEY` | No | 64 hex characters (`openssl rand -hex 32`) that encrypt stored secrets. Without it, a key is generated in `$DATA_DIR/.encryption-key`. The variable wins over the file |
| `VECTOR_STORE` | No | `auto` (default), `lancedb`, `pgvector`, or `milvus`. See [Vector Stores](/enterprise/deployment/vector-stores) |
| `VECTOR_DATABASE_URL` | No | Postgres connection string for pgvector, if it differs from `DATABASE_URL` |
| `PG_VECTOR_POOL_MAX` | No | pgvector connection pool size per replica (default: `5`) |
| `MILVUS_ADDRESS`, `MILVUS_TOKEN`, `MILVUS_USERNAME`, `MILVUS_PASSWORD`, `MILVUS_DATABASE` | No | Milvus connection settings |
| `CONTEXT7_API_URL` | No | Base URL for license checks, usage reports, and cloud library queries (default: `https://context7.com/api`) |
| `NODE_EXTRA_CA_CERTS` | No | Path to a PEM bundle of extra CA certificates. The server trusts it for all outbound HTTPS, and git uses it too |
| `GIT_TLS_INSECURE` | No | `true` or `1` turns off TLS verification for all outbound HTTPS and git. Use it only for testing |
| `AWS_REGION`, `AWS_DEFAULT_REGION`, `AWS_BEARER_TOKEN_BEDROCK`, standard AWS credential variables | No | AWS Bedrock authentication. See [AWS Bedrock](/enterprise/integrations/aws-bedrock) |
| `LOG_MAX_SIZE_MB` | No | Size of the log file before it rotates (default: `10`). Logs are JSONL in `$DATA_DIR/logs/context7.jsonl` |
| `LOG_MAX_FILES` | No | Number of rotated log files to keep (default: `3`) |
| `NOTION_REQUESTS_PER_MINUTE` | No | Notion API rate (default: `180`). The only other accepted value is `600` |
| `MAX_FILES`, `PARSE_CONCURRENCY`, `PARSE_TIMEOUT`, `NOTION_MAX_PAGES`, `GOOGLE_DRIVE_MAX_FILES` | No | Default values for the [parsing settings](#parsing-settings). A value saved in the dashboard wins |

<Note>
Provider and model selection, non-Bedrock provider keys, and git tokens are configured through the setup wizard and can be updated anytime from the Settings page in the web UI. There are no environment variables for git tokens (such as `GITHUB_TOKEN` or `GITLAB_TOKEN`) or provider API keys. Bedrock is the exception for authentication: it can use `AWS_BEARER_TOKEN_BEDROCK`, standard AWS credential environment variables, a mounted shared profile, or a workload IAM role. See [AWS Bedrock](/enterprise/integrations/aws-bedrock) for the supported credential chain.
</Note>

### AI Provider Settings

Configured via the **Settings** page in the web UI.

| Setting | Description |
|---|---|
| LLM Provider | `openai`, `anthropic`, `gemini`, `bedrock`, or custom |
| LLM API Key | API key for your chosen provider; optional for Bedrock with workload credentials |
| LLM Model | Model name or Bedrock model/inference-profile ID |
| AWS Region | Region used for Bedrock LLM and embedding requests |
| Base URL / Bedrock endpoint | Custom OpenAI-compatible endpoint, or an optional Bedrock Runtime endpoint |

### Embedding Settings

By default, Context7 uses the same provider as your LLM for generating embeddings. You can configure a separate embedding provider if needed.

| Setting | Description |
|---|---|
| Embedding Provider | `openai`, `gemini`, `bedrock`, or custom |
| Embedding API Key | Separate key; inherits the LLM key only when both use the same provider |
| Embedding Model | Embedding model name, such as `text-embedding-3-small` or `amazon.titan-embed-text-v2:0` |
| Embedding base URL / Bedrock endpoint | Custom embedding endpoint, or an optional Bedrock Runtime endpoint |

See [AWS Bedrock](/enterprise/integrations/aws-bedrock) for IAM, model, region, and private-network configuration.

### Decision Model

Optionally, a decision model can classify pages, check for duplicate snippets, and rerank search results in place of the language model. It is faster and costs less for these yes/no decisions. See [Decision Models](/enterprise/decision-models) to turn it on.

### Parsing Settings

Configured in **Settings → Indexing → Parsing**. For the settings with an environment variable, a value saved in the dashboard wins; the variable only sets the default.

The three count limits (files per library, Notion pages, Google Drive files) also offer **No limit**. Setting their environment variable to `0` does the same. Without a limit, a very large source can take a long time and make many LLM calls. File timeout and the concurrency settings always have a bound.

<Frame>
  ![The Max files per library setting with its list open and No limit selected](/images/enterprise/settings/parsing-no-limit.png)
</Frame>

The settings with an environment variable apply at the next parse on every replica. The first three apply at once on the replica that saves them; in a [multi-replica deployment](/enterprise/deployment/scaling), other replicas pick them up when they restart.

| Setting | Default | Range | Env fallback | Description |
|---|---|---|---|---|
| Max concurrent parses | `1` | 1–10 | — | Parses each replica runs at the same time |
| Max concurrent LLM requests | `5` | 1–64 | — | Requests in flight to the language model, shared by parsing and search |
| LLM timeout | `120` s | 30–1800 s | — | How long to wait for the model on one page |
| Max files per library | `500` | 1–100000, or no limit | `MAX_FILES` | Documentation files a repository parse reads, or pages a website or llms.txt parse keeps. Extra files are skipped and logged |
| Files parsed in parallel | `5` | 1–64 | `PARSE_CONCURRENCY` | Files one parse processes at the same time |
| File timeout | `500` s | 30–3600 s | `PARSE_TIMEOUT` | How long one file may take. The parse skips a file that takes longer |
| Max pages per Notion library | `10000` | 1–100000, or no limit | `NOTION_MAX_PAGES` | A Notion selection with more pages is refused |
| Max files per Google Drive library | `10000` | 1–100000, or no limit | `GOOGLE_DRIVE_MAX_FILES` | A Google Drive selection with more Docs and Slides is refused |

<Frame>
  ![The Parsing settings page with concurrency, timeout, and file limit settings](/images/enterprise/settings/parsing-settings.png)
</Frame>

### Git Access Tokens

Configured via the **Settings** page in the web UI.

| Setting | Description |
|---|---|
| GitHub Token | GitHub Personal Access Token. Required for GitHub repositories |
| GitLab Token | GitLab token. Required for GitLab repositories |
| GitLab **Server URL** | Your self-hosted GitLab host, such as `gitlab.your-company.com`. In the GitLab section, select **Self-hosted**, then enter it in **Server URL** |

You only need tokens for the platforms you use. If you only parse GitLab repos, you don't need a GitHub token, and vice versa. Create tokens with `repo` scope (GitHub) or `read_repository` scope (GitLab) for private repository access.

The GitLab token is sent only to `gitlab.com` and the host in **Server URL**.

## Access Control

Admin credentials are set during first login (default: `admin` / `admin`). Change these immediately after setup via **Settings > Change Credentials**.

Signed-in members and their personal API keys can always parse and refresh libraries. Delete, cancel parse, and support bundle downloads are for admins, unless the delete and support bundle switches below open them to members. The Settings page lets you open some of these operations to anonymous callers (no session and no API key), and control MCP and API search access.

<Frame>
  ![The Non-admin permissions card with the anonymous parse, refresh, support bundle, and delete switches off](/images/enterprise/settings/non-admin-permissions.png)
</Frame>

| Permission | Default | Description |
|---|---|---|
| Allow anonymous parse | Off | Allow anonymous callers to trigger parsing |
| Allow anonymous refresh | Off | Allow anonymous callers to refresh libraries. Notion and Google Drive libraries stay admin-only |
| Allow anonymous delete | Off | Allow anonymous callers and members to delete libraries and cancel parses |
| Allow anonymous support bundle | Off | Allow anonymous callers and members to download the support bundle |
| Require MCP authentication | Off | Require a session or personal API key for `/mcp`, `/api/v2`, and the library, log, and queue read endpoints. See [Authentication](/enterprise/api/authentication#anonymous-access) |

<Note>
Earlier versions allowed anonymous parse and refresh by default. If you never saved these switches, they are off after an upgrade, and scripts that call these endpoints without an API key get `403`. Add a personal API key, or turn the switch on.
</Note>

When MCP authentication is enabled, each user creates personal keys from **Personal Settings > API Keys**. Clients send the key as `Authorization: Bearer <key>`.

### Recover admin access

If you lose the admin password, or an SSO misconfiguration locks you out, run the `reset-password` script inside the container. It resets a local admin account and turns password sign-in back on. See [Docker](/enterprise/deployment/docker#recover-admin-access) or [Kubernetes](/enterprise/deployment/kubernetes#recover-admin-access).

## Policies

Policies let you control which public documentation from the Context7 cloud is accessible to your on-premise instance. They do not affect locally parsed on-premise content.

Access Policies from **Settings > Policies** tab. Requires admin login and a valid `LICENSE_KEY`.

For details on source type toggles and library filters, see [Customizing What Is Retrieved](/security/data-privacy#customizing-what-is-retrieved).

## Network and Data Flow

Besides your AI providers, git hosts, and connected sources, an instance with an online license contacts Context7 Cloud. It validates the license every hour, sends a daily usage report, and queries Context7 Cloud for public library results. The usage report holds the license key, call counts per endpoint, the number of active API keys, and the app version; it holds no query text. Query text for public library results is masked for secrets before it is sent. The content of local libraries is never sent. Per-user usage stays on the instance.

An offline license (`ctx7off.` prefix) is verified locally and makes none of these calls. The server does not apply `HTTP_PROXY` or `HTTPS_PROXY` to its own calls. For the full egress list, `CONTEXT7_API_URL`, and private CA setup, see [Docker](/enterprise/deployment/docker#network-access) or [Kubernetes](/enterprise/deployment/kubernetes#networking-requirements).

## Hosting

- Serve Context7 at the root of a host name, such as `https://context7.internal.yourcompany.com`. Hosting under a sub-path is not supported.
- Behind a reverse proxy, Context7 uses `X-Forwarded-Host` and `X-Forwarded-Proto` to build SSO redirect URLs. Configure the proxy to set these headers and overwrite any values the client sends.
